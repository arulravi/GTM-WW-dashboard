**Critical bug fix: "Save commentary" showed "saved ✓" even when the save failed (2026-08-06).** Root cause in `dashboard.html`'s `saveCommentary()`: the fetch chain called `done()` (which set the "saved ✓" text) **unconditionally** — `.then(r=>r.json()).then(j=>{ if(j.ok...){...} done(); })` ran `done()` regardless of `j.ok`, and `.catch(()=>done())` showed success even on a network error. So a down server, a 500, or a dropped connection all silently displayed "saved" while nothing actually persisted — exactly what the user reported, and now more people are using the app so a lost note is a real risk, not hypothetical.

Fixed by splitting into `showOk()` (only reachable when `r.ok && j.ok && j.commentary` are all true) and `showFail(why)` (shown on any failure — bad HTTP status, `{ok:false}` response, JSON-parse failure, or a rejected fetch) — `showFail` sets the message red (`var(--bad)`), logs to console, and **does not auto-fade** (stays visible until the next attempt), unlike the normal green fade-after-1.8s success message. `localStorage` is still written first regardless (instant local safety net), so no data is lost even on a server failure — only the misleading "saved" claim is gone.

Also hardened `server.py`'s `/api/commentary` POST handler for real multi-user load: added a module-level `_commentary_lock = threading.Lock()` around the whole read-merge-write (previously two people saving at once, each a separate thread under `ThreadingHTTPServer`, could both read the same file, merge in memory, and the second write would silently drop the first's addition — a real lost-update race). Also switched the write itself to atomic (`write to commentary.json.tmp<pid>` + `os.fsync` + `os.replace`), so a crash or concurrent GET mid-write can never see a half-written/corrupt file.

**Fixed the REAL bug behind "still cut off" (2026-08-07), both apps -- the width fix above was real but incomplete.** User's next screenshot showed the table's own header row ("COST ELEMENT" etc.) rendering partially UNDERNEATH the app's sticky logo/filters/tabs bar when scrolled -- a different bug than the width one, same root-cause *pattern* as the earlier drill-through fix: the base `th{position:sticky;top:0}` rule (and `#hcWalk thead th{top:0}`) sticks the table header to the very top of the viewport, but the app's own `<header>` (containing the hbar + `nav.tabs`, both wrapped in one `<header>` element) is ALSO `position:sticky;top:0;z-index:50` -- two things pinned to the same `top:0` means the (lower-z-index) table header renders behind/under the (higher-z-index) app header instead of settling in below it.

Fix: added a `--header-h:0px` CSS custom property, changed both sticky table-header rules to `top:var(--header-h)` instead of `top:0`, and added `syncHeaderHeight()` (`document.documentElement.style.setProperty("--header-h", header.offsetHeight+"px")`) wired up three ways for robustness: once at initial "wire up", on `window resize`, via a `ResizeObserver` on the `<header>` element itself (catches filter-row wrapping / dark-mode height changes automatically), AND **at the end of every `renderAll()` call** (added after finding the ResizeObserver alone left a stale/transient height briefly on initial load in one test -- filter dropdown option counts change per tab and can nudge header height, so re-measuring after every render closes that gap). Chose a *measured* height over a second hardcoded guess deliberately, having already been burned once by a hardcoded `top:49px` in the drill-through page.
